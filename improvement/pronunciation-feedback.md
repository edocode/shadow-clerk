## 背景

`clerk-practice` の発音練習は、いま「音声認識に通るかどうか」で判定している
（`SKILL.md` の「発音」節）。Whisper が文脈で誤りを修復してしまうのを避けるため、
単語単体やミニマルペアで試す設計になっている。

この方式は依存ゼロで多言語に効く代わりに、**通った / 通らなかった の2値しか出ない**。
「どう外しているか」が分からないので、直し方を具体的に言えない。

音素レベルのフィードバック（どの音をどう外したか）を足せないか検討した。

## 採る方針（C案）

daemon は決定的な処理だけを持ち、解釈は skill 側の Claude がやる。

```
課題テキスト ──espeak-ng (G2P)──▶ 期待IPA
                                     │
発話PCM ──wav2vec2 音素認識──▶ 実測IPA
                                     ▼
                     daemon はこの2本のIPA列を返して終わり
                                     ▼
            「どこがどう違うか」「どう直すか」は Claude が読み解く
```

多言語を前提にする以上、「/ɹ/ が /l/ になった人にどう直させるか」を言語ごとに
コード化するのは不可能で、学習者の母語によっても説明が変わる。そこは LLM の領分。
逆に音素認識は LLM にはできない。**能力の境界で素直に割れる**のが利点。

副次的に、アライメント方式や説明の質を skill のバージョンアップだけで改善できる
（daemon の再インストールが要らない）。

### 検討して落とした案

- **A案: daemon が判定まで持つ** — 置換・脱落・挿入の検出とラベル付けまで Python でやる。
  再現性が高く履歴の集計もしやすいが、言語ごとの知識をコードに抱え込むので多言語で破綻する。
  単一言語なら最善
- **B案: skill 側で全部** — daemon は直近発話の PCM を返すだけ。daemon が薄く保てるが、
  `clerk-practice` の `allowed-tools` が curl 限定なので許可設計のやり直しが必要で、
  毎回のモデルロードでレイテンシが厳しい

## モデル選定

`facebook/wav2vec2-xlsr-53-espeak-cv-ft` を使う。

当初候補にした `facebook/wav2vec2-lv-60-espeak-cv-ft` は**事前学習が英語のみ**
（英語6万時間の `wav2vec2-large-lv60` 起点）で、多言語性は CommonVoice の
ファインチューンだけから来ている。多言語前提なら 53言語の多言語事前学習 XLSR-53 起点の
兄弟モデルが正しい。

- 約57の言語コード、Apache 2.0、16kHz 入力、IPA 392語彙の CTC 出力
- ディスク 1.2GB
- `phonemize()` が特定の transformers バージョンでクラッシュする既知の不具合があり、
  バージョン固定が要る（huggingface/transformers#45198）

## 検証した問い と 事前基準

> 実測IPAは、学習者の発音の誤りを「拾える」かつ「誤って指摘しない」レベルにあるか。

本命の合否は感度ではなく**誤検出率**。正しく言えているのに「R が違います」と言う機能は、
学習ツールとして致命的に信用を失う。

事前に決めた基準（英語で測定）:

- go: フロア誤差 PER 10%未満 **かつ** ミニマルペアが別IPAに弁別できる
- no-go: PER 20%超 → 音素軸を諦めるか audio-LLM に切り替え

## 結果

| 測定 | 結果 | 判定 |
|---|---|---|
| フロア PER（実人間の連続発話・正規化後） | **9.10%** | go 基準クリア |
| 学習上重要な対立の保存 | **8/8** | R/L, sheep/ship, think/sink, berry/very ほか全部 |
| 誤り検出 | **12/12** | |
| CPU レイテンシ | RTF 0.10–0.15（2.3秒の音声で236ms）、ロード1.4秒 | リアルタイムに余裕 |
| システム依存 | espeak-ng は**ホイールで入る（sudo不要）** | 懸念が消えた |

フロア測定は LibriSpeech test-clean（ネイティブ実音声）20発話。
レイテンシは GPU なし・CPU 8スレッド。

### 正規化層が必須

生のIPA比較は使えない。**PER 13.31% → 9.10%** の差は、ほぼ全部が発音の質ではなく
**表記体系のズレ**だった。

```
ᵻ → ɪ      ɐ → æ      ɜː → ɚ     ə → ɐ
ɔːɹ → oː   ɹ → ɚ      ɔ → ɑː     ɾ → t
```

espeak の G2P が使う記号とモデルが出す記号が違うだけで、誤りではない
（`ɾ → t` はネイティブのフラップという異音）。これを素通しすると、ネイティブ並みに
正しく言えている発話を片端から「違います」と指摘することになる — 事前に
致命的と決めた、まさにその失敗モード。

等価クラスへの正規化で解消する。マージするのは espeak とモデルの表記揺れだけで、
**学習者にとって意味のある対立（ɹ/l, iː/ɪ, θ/s, b/v）は意図的に残す**。
正規化後も上記8対立はすべて dist=1 で保たれることを確認済み。

## 最大の発見 — 現行の課題の出し方と衝突する

```
単語単体 ("right")              PER 13.1〜20.2%  ← 実行ごとに振れる。不安定
キャリア文 ("Say right again.")  PER  1.32%
```

同じ単語・同じモデルで、違いは文脈の有無だけ。単体だと語末閉鎖音と語頭子音が崩れる
（`ship`→/ɕ e t/、`glass`→/b l a s/、`three`→/ɹ i/）。約0.5秒の孤立単語は
wav2vec2 にとって分布外。

**ここが現行設計と真逆になる。** いまの `clerk-practice` が単語単体を使っているのは、
Whisper が文脈で誤りを*修復してしまう*のを避けるため。しかし音素モデルは言語モデルを
持たないので修復が起きず、**文脈は害ではなく必要な助けになる**。

→ C案を入れるなら、課題の出し方を「単語単体」から「文 / キャリア文」に変える必要がある。
スキル側の変更であり、語学練習としてはむしろ自然な方向。

## 正当に疑うべき点

### 1. TTS を使った数字は circular

ベースライン音声の生成に piper を使ったが、piper は espeak の音素列から合成する。
つまり「espeak の期待IPA vs piper音声の認識IPA」は出来レース。短文の PER 0.00% は
信用できない。**信用できる絶対値は LibriSpeech の 9.10% だけ**。

ただし「単体 vs キャリア文」は同一条件内の相対比較なので結論は有効
（出来レース条件ですら単体が崩れる＝実音声ではもっと崩れる）。

### 2. 実際の非ネイティブ音声が未検証 ← 最大の残存リスク

今回の「誤り」はすべて「別の実在の単語を言う」で模擬したもので、categorical な置換。
実際の学習者の誤りは gradient で、日本語話者の /r/ は ɹ でも l でもない中間音。
モデルがそれを**正解側のカテゴリにスナップして誤りを隠す**可能性がある。
これが起きると機能は成立しない。

### 3. 検出 ≠ 正しい診断

12組中5組で、差分が真の誤り位置とズレた。例: fan→van は `f→v` ではなく
母音の違いとして検出された。

C案の「測るのは daemon、読み解くのは Claude」という分け方はここで効く。
ハードコードされたルールが「あなたのAが違う」と断言する代わりに、
Claude が両方のIPA列を見て判断できる。

## 設計に確定で反映されること

1. **正規化層が必須コンポーネント**（生のIPA比較は使えない）
2. **課題は文単位で出す**（単語を練習したいならキャリア文に埋める）
3. **espeak-ng はホイール経由**（`espeakng-loader` + `phonemizer-fork`）。
   システム依存の懸念は設計から外せる

## 未解決

- **実際の非ネイティブ発話での誤検出率**（上記2）。これが通らなければ C案は成立しない。
  設計ドキュメントを書く前にここを潰す
- 英語以外の言語での実精度。57言語リストに載っていることと使い物になることは別
- モデルを常駐させるか、練習モードに入ったときだけロードするか（ロード1.4秒なので
  オンデマンドで足りる可能性が高い）
- API の形（課題の事前登録 → 次の発話で解析 → 結果取得）

## 実話者での検証（追記）

非ネイティブ話者1名（日本語母語）に6文を2条件で読んでもらった。
「natural（ふだんどおり）」「accented（意図的に日本語の音に寄せる）」。
マイクから `pw-record` で 16kHz モノラル。

| 条件 | PER |
|---|---|
| natural | 35.64% |
| accented | 61.39% |
| （参考）ネイティブ連続発話のフロア | 9.10% |

### モデルは非ネイティブ音に別の記号を使う ← 重要

ネイティブ発話1640音素中、モデルが出した記号の内訳:

| 記号 | ネイティブでの出現 |
|---|---|
| `ɹ`（英語の R） | 55 |
| **`r`（タップ/ふるえ音）** | **0** |
| `æ` | 68 |
| **`a`（日本語のア）** | **1** |
| `ɛ` | 41 |
| **`e`（日本語のエ）** | **0** |

`r` `a` `e` は実質、非ネイティブの実現にだけ割り当てられている。
非ネイティブ話者の録音にはこれらが繰り返し出た。

**設計上の帰結: 正規化で `r→ɹ` や `a→æ` をマージしてはいけない。**
ここに信号が乗っている。正規化層は espeak の記号体系ではなく
**モデルの実出力インベントリから作り、非ネイティブ音声で検証する**必要がある。
（初版の正規化はネイティブ発話の置換リストから作ったので、この区別を持っていなかった）

### 単語単位の結果

| | natural | accented |
|---|---|---|
| `right` の R | クリーン | ɹ→d |
| `grass` の R | クリーン | ɹ→∅ |
| `glass` の L | l→**r**（タップ） | l→r |
| `light` の L | l→∅（脱落） | l→r |
| `she` / `ship` の ʃ | ʃ→s | ʃ→s |
| `three` の R | ɹ→**r** | ɹ→l |
| `think` の θ | θ→f | θ→s |

natural はノイズではなく**一貫したプロファイル**を出している。
R は正しく出ていて L だけが崩れる、という選択性は偶然では出にくい。
`glass` の `l→r` と `she` の `ʃ→s` は条件をまたいで再現した。
日本語話者の典型パターン（L のタップ化、「シ」[ɕ] と ʃ のズレ）とも一致する。

### この検証の限界

**元の問い（誤検出率）には答えられていない。** natural は「正しく発音できている人が
誤指摘されないか」を測る条件のはずだったが、話者本人の自己申告どおり実際の誤りを
含むため、35.64% は真陽性と偽陽性の混合で分離できない。

明らかにモデル側のノイズに見えるものもある: `clean`→/ɡ ɹ i n/（green）、
`sweet` の w と t の脱落、`he` の h 脱落、`hat` の母音脱落。

また `is` の `z→ð` が6文中4文で系統的に出た。話者の一貫した癖か、
正規化の穴かを判別できていない。

### 未解決（更新）

- **誤検出率の分離**。必要なのは次のどちらか:
  - ネイティブ/ニアネイティブ話者による同一6文の録音（偽陽性のフロアを直接測る）
  - **同一話者による同一文の反復テイク**（安定性を見る。ネイティブ話者が要らないので安い。
    モデルがノイズを出しているなら反復間で結果が割れ、実観測なら一致する）
- 正規化層をモデルの出力インベントリから作り直す

## 反復テイクと摂動テスト（追記・決定的）

### 反復テイク

同一話者が同一6文を2回読んだ（natural / natural2）。

```
完全一致: 対象語 2/13 (15%)   全語 4/30 (13%)
take1 PER 35.64%   take2 PER 30.69%
```

判定が逆向きに飛ぶ語があった:

| 語 | take1 | take2 |
|---|---|---|
| `think` | θ→f | クリーン |
| `she` | ʃ→s | クリーン |
| `very` | v→∅ ɛ→b ɹ→t | クリーン |
| `sink` | クリーン | s→θ |
| `seat` | クリーン | s→f |

再現したもの:

```
light  l→∅        両テイク完全一致
hat    A→∅ t→a    両テイク完全一致
sat    A→a        両テイク完全一致
is     @→i z→ð    両テイク完全一致
glass  l→r / l→ɹ  どちらも L が誤り（なった先は不一致）
three  ɹ→r        両テイクで出る
```

粒度別の一致率: 「何になったか」まで 15% / 「誤りがあるか」だけ 62% (8/13)。

### 摂動テスト — テイク間の差はモデルのノイズか、話者の揺れか

反復テイクの食い違いだけでは、モデルのノイズと話者の揺れを区別できない。
take1 で実際に θ→f と言い take2 で正しく言ったなら、モデルは両方とも
正しく報告している。

**発音を一切変えない摂動**（ゲイン ×0.9 / ×1.1、時間シフト +10ms / +25ms、
-40dB のノイズ付加）を同一録音に加えて、判定が飛ぶかを測った。

```
摂動での判定変化
  「誤りの有無」が反転   :  4/75  ( 5%)
  「何になったか」が変化 : 16/75  (21%)

（比較）take1 vs take2 の有無反転 : 5/13 (38%)
```

**5% 対 38%。** ゲイン変化では6文すべてで変化ゼロだった。
モデルは有無レベルでは十分安定しており、テイク間の食い違いは
モデルのノイズでは説明できない。**話者の発音の揺れが実在する。**

→ **モデルは実在するものを測っている。**

## ラベル付き検証 — 1発話ごとの精度（決定的）

反復テイクの食い違いは、モデルのノイズと話者の揺れを区別できない。
そこで**意図した語を正解ラベルとして使う**設計に変えた。

課題文 `The glass is on the grass.` は、`glass` の /l/ と `grass` の /ɹ/ を
同じ `/ɡ_/` 文脈に1つずつ含む。各テイクが両方を、完全に同じ録音条件で提供する。

### 結果

| 条件 | glass (意図 /l/) | grass (意図 /ɹ/) |
|---|---|---|
| natural 10本 | r:6 ɹ:3 l:1 | ɹ:9 ∅:1 |
| natural 残り5本（再掲） | r:5 | ɹ:5 |
| L を意図的に誇張 5本 | d:1 l:1 ɹ:2 ∅:1 | ɹ:5 |

**ラベル既知の /ɹ/ に対する1発話ごとの精度: 19/20 ≈ 95%。**
同一発話内に常にコントロールがある状態で、R側は一切ブレていない。

誇張時は `r` がゼロになり d/l/ɹ/∅ に散った。
**モデルは1つの答えに固着せず、調音の変化を追っている。**

### 母音挿入が検出された

誇張テイク5本中4本で、`ɡ` と liquid の間に `u` が入った。

```
ɡ u ɹ a f s      ɡ u ɹ a θ      ɡ u dʒ a s      u l a s
```

「グラス」。L を出そうと力んだ結果、子音連結が割れて母音が挿入された。
日本語話者の典型パターンで、ASR の素通しでは絶対に取れない情報。

### この控えテストの限界

「きれいな英語の /l/ を出したら l と出るか」を見るはずだったが、
発話されたのは /ɡl/ ではなく /ɡul/ だった。したがって
「モデルが l を聞けない」のか「l が出ていない」のかは、この5本では決まらない。
clean な /l/ は語頭（`light`, `love`）の方が出しやすいので、詰めるならそこ。

## 語頭 /l/ での追試 — 残っていた穴が埋まった

`glass` の結果だけでは「モデルがこの話者の /l/ を聞けない」可能性を排除できなかった。
語頭 /l/ は連結より出しやすいので、`Turn right at the light.` で追試した。
`right`（語頭 ɹ）がコントロール、`light`（語頭 l）がテスト。

```
right (語頭 ɹ) : ɹ 10/10
light (語頭 l) : l 5/10   r 3   ɹ 1   ∅ 1
glass (連結 l) : l 1/10   r 6   ɹ 3      ← 前回
```

**モデルはこの話者の `l` を出せる。** 語頭で 5/10。
「モデルが l を聞けないだけ」という可能性は消えた。測定は検証済み。

### 位置効果

| /l/ の位置 | `l` として出た率 |
|---|---|
| 語頭（`light`） | 5/10 |
| 子音連結（`glass`） | 1/10 |

この話者の L は語頭では半分ほど出ており、連結で崩れる。
力むと母音が挿入されて「グラス」になる前回の所見と一貫する。

### 中間的な調音が可視化される

take 07 / 10 では liquid が2つ出た。

```
r l aɪ        l r aɪ
```

タップと l の両方。中間的で不安定な調音そのもの。
**「l が何になったか」という素朴なルールでは扱えない形**であり、
生の IPA 対を Claude に渡す C案なら「両方出ている＝調音が不安定」と素直に読める。
C案の境界の引き方を支持する材料。

### /ɹ/ の最終精度

ラベル既知の /ɹ/ に対する1発話ごとの精度:

| 課題 | 結果 |
|---|---|
| `grass`（natural 10 + 誇張 5） | 14/15 |
| `right`（語頭 10） | 10/10 |
| **合計** | **24/25 ≈ 96%** |

これが (A)「この発話に対する判定は正しいか」の最終的な数字。

### この話者のプロファイル（参考）

| 音 | 状態 |
|---|---|
| R | ほぼ完璧（24/25） |
| L（語頭） | 約50%。l とタップを行き来する |
| L（連結） | 約10%。ほぼタップ。力むと母音挿入 |
| ʃ（`she` `ship`） | s になる |
| θ | 不安定（f や s になる） |

ASR の素通しでは、この粒度の所見は一切得られない。

## 単体の単語の追試（実人間）

当初の「単語単体は不可」は TTS だけが根拠だった。piper は espeak の音素列から
合成するので出来レースであり、かつ piper 自身が単語単体の合成を苦手としている
可能性もあった。実人間で測り直した（`right` `light` `grass` `glass` × 5テイク）。

```
単体の PER(全体) : 54.29%
（参考）TTS 単体 13〜20% / TTS キャリア文 1.32% / ネイティブ連続発話 9.10%
```

**実人間の単体発話は TTS が示唆したよりさらに悪い。** 結論は変わらないが、
崩れ方に明確なパターンがあることが分かった。

| 語 | 単体 | 文の中 | |
|---|---|---|---|
| `right`（語頭の単独子音） | 5/5 | 10/10 | 無傷 |
| `light`（語頭の単独子音） | 2/5 | 5/10 | ほぼ同等 |
| `grass`（語頭が連結） | 2/5 → **9/15** | 14/15 | 大きく劣化 |
| `glass`（語頭が連結） | 2/5 → **7/15** | 1/10 | — |

（`grass` `glass` は後から10テイク足して n=15 にした。下の「追試」を参照）

```
right 04/05  /ɹ aɪ/      語末の t が脱落（0.35秒）
grass 01/04  /ɹ a/       語頭の ɡ が消え、語末の s も脱落
glass 01/03  /k @ l a/   ɡ が k に、s が脱落
```

語末子音は `grass` `glass` で5本中4本、`right` でも5本中2本落ちた。
語頭の連結も崩れる。一方で**語頭の単独子音は無傷**、核母音も概ね残る。

### 追試 — `grass` / `glass` を15テイクに増やす（追記）

5テイクでは「たまたま」が残る。同じ2語をあと10テイク録って n=15 にした。

```
grass  正解 2/5 → 合計  9/15 (60%)   内訳 {ɹ: 9, ∅: 5, r: 1}
glass  正解 2/5 → 合計  7/15 (47%)   内訳 {l: 7, d: 5, r: 2, ∅: 1}
発話長 session1 0.53s / 0.56s → session2 0.54s / 0.61s（丁寧になった様子はない）
```

語ごとの PER（全テイク、正規化後）:

| 語 | n | PER |
|---|---|---|
| `right`（語頭の単独子音） | 5 | 13.3% |
| `light`（語頭の単独子音） | 5 | 26.7% |
| `grass`（語頭が連結） | 15 | 66.7% |
| `glass`（語頭が連結） | 15 | 100.0% |

当初20本で測った 54.29% より悪くなったのは、増やした10本がどちらも
語頭連結の語だったため。**語頭の単独子音と語頭連結の差が、テイクを増やしても残る。**

### 単体での摂動テスト（追記）

文での摂動テスト（5%）と同じ摂動（ゲイン ±10%、+10ms / +25ms シフト、-40dB ノイズ）を
単体の録音20本に当てた。発音は一切変えていない。

```
（比較）文での「誤りの有無」反転 : 4/75 (5%)
```

**単体はモデル側のノイズも2倍だが、それでも 10% では 54〜70% の PER を説明できない。**
残りは再現するバイアス。

### キャリア文での実測（追記）— 身代わりは実際に起きている

`Say <word> again.` を同じ話者で5テイクずつ。対象語だけを切り出して採点した。

| 語 | target | 単体 | キャリア文 | 完全な文 |
|---|---|---|---|---|
| `right` | ɹ | 5/5 | 5/5 | 10/10 |
| `light` | l | 2/5 | 2/5 `{r:3, l:2}` | 5/10 |
| `grass` | ɹ | 9/15 | **5/5** | 14/15 |
| `glass` | l | 7/15 | **0/5** `{r:4, ɹ:1}` | 1/10 |

`grass` は語頭連結 `ɡɹ` が5本とも戻り、語末 `s` も4/5 で戻った
（対象語の PER 66.7% → 30.0%）。一方 `glass` は文脈があっても戻らない。
この話者の `l` そのものが弱く、単体 7/15・文 1/10・キャリア文 0/5 と一貫して低い。
**キャリア文は端の劣化を救うが、話者の実際の調音の問題は救わない**（救ってはいけない）。

そして**キャリア語のほうが壊れる**:

```
Say right again.  → /f e   ɹ aɪ t  a ɡ e ŋ/
                  → /f eɪ  ɹ aɪ t  a ɡ @ ŋ/
                  → /f e   ɹ aɪ t  a ɡ i ŋ/
Say grass again.  → /s eɪ  ɡ ɹ a s  a ɡ i ŋ/
```

`Say` が `f e` に、`again` が `a ɡ i ŋ` になっている。対象語は無傷。
キャリア文**全体**の PER は 50.53% で、単体の 54.29% とほとんど変わらない。

→ **発話全体の PER は対象語の出来をまったく表さない。対象語だけを見る。**

### 検討して却下した案 — TTS を基準にする（追記）

期待IPA を espeak の G2P ではなく、同じ文を TTS に喋らせて同じモデルに通した
結果にすれば、モデルのバイアスが引き算で消えるのでは、という案を測った
（TTS 3回のうち最も近いものを基準に採る）。

```
--- 単体 ---                      --- キャリア文 ---
word    espeak基準  TTS基準  改善     word    espeak基準  TTS基準  改善
right     13.3%     13.3%   +0.0%    right     0.0%      0.0%    +0.0%
light     26.7%     26.7%   +0.0%    light    20.0%     20.0%    +0.0%
grass     66.7%     58.3%   +8.3%    grass    30.0%     30.0%    +0.0%
glass    100.0%     96.7%   +3.3%    glass    75.0%     75.0%    +0.0%
```

**救済にならない。** 改善は単体の2語で 8.3% / 3.3%、キャリア文では完全にゼロ。
崩れ方が声ごとに違うのが理由で、TTS の基準自体が安定していない:

```
TTS glass 単体 ×3 : /b @ l A s/  /b l A s/  /p l ɛ s/     ← ɡ→b, p
人間 glass 単体    : /k @ l a/  /k u d a θ/  /ɡ @ d a θ/   ← ɡ→k ＋ 母音挿入
```

TTS は `ɡ` を `b`/`p` に倒し、人間は `k` に倒したうえで母音を挿入する。
**同じ「短い音声のバイアス」ではないので、引き算の対象にならない。**

→ **期待IPA は espeak の G2P のまま据え置く。**

### 改訂された制約

- 裸の単語が使えるのは**語頭の単独子音の対立だけ**（`right`/`light` 等）
- 語頭の連結・語末子音・母音の質は文脈が要る
- 実用上は**キャリア文**（`Say right again.`）を既定にする。
  文脈の利点を保ったまま、1語を集中的に練習する形態は維持できる


## 結論（最終）

**1発話ごとのフィードバックは成立する。** 以前に書いた「集約が必須」は誤り。
反復テイクの食い違いは話者の揺れであって、1回ごとの判定の正しさを否定しない。
その場の発話の誤りを指摘できれば、学習ツールとして有用。

### 設計に反映されること（最終版）

1. **課題文には対立ペアを両方入れる**（`The glass is on the grass.` /
   `Turn right at the light.`）。毎発話が自分のコントロールを持つので
   「R は出ているのに L が出ていない」という**相対判断**ができる。
   絶対的な閾値が不要になり、話者差・マイク差・体調差に強い
2. **正規化で `r→ɹ` `a→æ` をマージしない**。この検証では `r` と `ɹ` の区別が
   信号そのものだった。正規化層は espeak の記号体系ではなく
   モデルの実出力インベントリから作り、非ネイティブ音声で検証する
3. **課題は文またはキャリア文**。裸の単語は語頭の単独子音の対立に限る
   （実人間の単体発話 PER 54.29%、語末子音が落ちる）
4. **「何の音になったか」は Claude に渡してよいが、学習者への出力で
   言い切らせない**。摂動だけでも21%変化する。「R は出ているが L が
   タップになっている」のような相対的な言い方にする
5. espeak-ng はホイール経由（`espeakng-loader` + `phonemizer-fork`）。
   システム依存なし
6. 母音挿入のような**音素列の構造的な崩れも拾える**。これは C案で
   Claude に生の IPA 対を渡す設計の、予期していなかった利点

- **ニアネイティブ話者での偽陽性率**。今回の数字はすべて非ネイティブ話者1名のもの
- （解決済み: 日本語で検証し、多言語は v1 の対象外と決定）

## ブラインドテスト — Claude は生の ops から所見を出せるか

C案の「測るのは daemon、読み解くのは Claude」という境界そのものを検証した。
解析結果の JSON とスキルの指示文だけを、文脈を持たない Claude（Haiku）に渡し、
学習者に返す文を書かせて人手で採点した。正解キーは別ディレクトリに隔離。

### 第1弾（10件 × 2記号体系）

正解が「指摘しない」のケースを3件混ぜた（focus の語に差分なし／キャリア語だけ崩れている／
focus 内外とも全部崩れている＝入力品質を疑うべき）。

| | 明確な正答 |
|---|---|
| IPA 記号版 | 8/10 |
| ASCII 記号版 | 9/10 |

重要3件は2回とも通過。キャリア語が派手に崩れているケース（`Say`→`f e`、
`again`→`a ɡ i ŋ`）で、両方とも**対象語だけを見て「問題なし」**と答えた。
20観測すべてで、傾向としての断定はゼロ（すべて「今回の発話では」で始まる）。

### 第2弾（8件 × 2記号体系 × 2回）

第1弾で「曖昧な記号が focus の語に一度も出ない」というテスト設計の欠陥が判明したため、
記号を focus の音素そのものに置いて作り直した。focus も音素レベルにした。

**4本すべて 8/8 満点。** 記号体系の差は出なかった。

- 同じ語で「母音だけ誤り」と「子音だけ誤り」を出し分けられた
- 最難関（r 性母音が R 子音として出ている）も4本とも正しく言語化
- ASCII 版は `R` を自力で `ɝ` に変換して出力した

ただし指示文に「母音か子音かを取り違えないこと」を入れてあるため、
示せたのは「**その指示があれば** ASCII でも安全」まで。
→ IPA 記号を採用する。理由は「ASCII が危険」ではなく、**IPA なら指示への依存が消える**から。

### 予期していなかった収穫

4本とも、指示していないのに調音の助言を自分で付けた。

```
「舌先を後ろに反らせたまま、口を丸めずに発音してみてください」
「唇は丸めず、舌の奥を後ろに引いて」
「舌先を上の歯茎につけ、舌の両脇から息を通す」
```

音素の差分から学習者向けの具体的な指導に変換できている。
daemon 側にこの知識を持たせるのは不可能なので、**境界の置き方が正しいことの直接の証拠**。

### このテストの限界

- 読ませたのは**人工的に構成した JSON** であり、実際のアライメント出力そのものではない。
  示せたのは「設計どおりの JSON なら読める」まで。end-to-end の実測ではない
- 全52観測（第1弾 10件×2 ＋ 第2弾 8件×4）。当初「28観測」と書いたのは数え誤り
- **調音の助言の正しさは採点していない。** 「助言を出せる」までで、「正しい助言を
  出せる」ではない。例として出た「口を丸めずに」は英語の R の指導として疑わしい
  （唇を丸める話者が多い）
- 正解キーを作った者と採点した者が同一。盲検なのは読ませた側だけ


### 確定した修正2点

1. **`focus` は語ではなく音素で指定する。** 語で指定すると、focus 語の中の
   フロア誤差（`æ→ɔ` 等）まで律儀に報告された。指示どおりの動作であり、
   ルールの方が誤っていた
2. **母音挿入は素朴なアライメントから読み取れない。** 2回とも失敗。
   実際は「ɡ と l の間に u が挿入」だが、編集距離は `l→u, æ→ɹ, +a, +f` と並べる。
   「余分な音が入っている」までは言えるが、位置と内容を特定できない

## 日本語での検証 — 多言語は成立しない

「正規化は多言語のハードルにならないか」という問いから、日本語で検証した。
話者はネイティブなので、出た差分は定義上すべて表記のズレのはず、という設計。

### 手前で止まった: espeak は漢字を読めない

```
今日はいい天気です
  → (en) tʃ aɪ n iː z (ja) l e̞ t ə | …     ← 漢字1文字ごとに「Chinese letter」
```

かな書きなら正しく音素化できる（`きょうは いい てんき です` →
`kʲ o̞ ɯᵝ h ä | iː | t e̞ ŋ k i | d e̞ s ɯᵝ`）。長短・清濁・促音・撥音も保持される。

**「espeak が約100言語の G2P を担う」という前提は一般には成り立たない。**
語彙的な読みの解決が要る表記体系で破綻する。

→ 設計に必須: **G2P の出力を使う前に検証する。** 言語切り替えマーカー `(en)` 等が
混ざっていたら期待IPA が壊れているので、その課題を拒否する。
壊れた期待IPA で比較すると、学習者が完璧に発音しても全音素が誤りとして出る。

### かな書きで測った結果

6文 × 3テイク = 18発話、414音素。

```
生の PER                     64.49%     （英語の生は 13.31%）
占有率による導出を適用した後    48.79%     （英語は 9.10%）
```

置換の中身が2層に分かれていた。

```
表記のズレ   ä→a 55 / o̞→o 22 / e̞→e 11 / ɯᵝ→u 6 / ɴ→ŋ,n 9 / ɕ→s 6 / ɽ→ɾ,r 8
説明できない  せんせい→θ e n θ e  （s が θ に）
             ちいさい→tʃ i f a i  （s が f に）
             にわ→n i v a         （w が v に）
             母音の脱落 37回
```

モデルが日本語の音をヨーロッパ言語の音素カテゴリに当てはめて聞いている。

### 導出パイプラインの誤り2点

**(1) union-find による推移閉包が全部を潰した。** `i~s`、`s~f`、`ɕ~s`、`e̞~θ`、
`e̞~e`、`i~e` が連鎖し、`i` `s` `e` `θ` `f` `ɕ` が1クラスになり、
`ɴ~n` が繋がって代表が `n` になった。PER が 19.92% に下がったのは改善ではなく、
全記号が同じになれば編集距離が縮むという当たり前の帰結。

**(2) 頻度ではなく占有率で判定すべきだった。** 表記のズレなら置換はほぼ全数で起きる。

```
採用  ä→a 55/69 (80%)   ää→a 3/3 (100%)
却下  o̞→o 22/42 (52%)  ɯᵝ→o 8/27 (30%)  ɕ→s 6/12 (50%)  s→f 4/13 (31%)
```

占有率3〜5割は「同じ音素が回ごとに違う記号になる」ことを意味し、
表記のズレではなく認識の不安定。占有率の基準は正しく機能し、連鎖版が誤って
採用した組をすべてはねた。**導出の手続きとしては、これが正しい形。**

### それでも日本語は使えない

```
きて   /k i t e̞/      vs きって  /k i t e̞/        潰れた
おばさん /o̞ b a s a ɴ/  vs おばあさん /o̞ b a s a ɴ/  潰れた
```

**促音**について、当初「汎用正規化の『同一記号の連続を圧縮』が潰した」と書いたが、
**これは誤りだった**（検証せずに推測で書いた）。デコーダの `group_tokens` を切って
生の出力を見ると:

```
かって  期待 k ä t t e̞
  group_tokens=True (既定)  : k a t d e
  group_tokens=False        : k a t d e
```

**どちらでも重子音は出ていない。** 正規化層が潰したのではなく、モデルが最初から
促音を出していない。長母音とまったく同じ状況。

（なお「連続圧縮は重子音を持つ言語で意味を壊しうる」こと自体は原理的には正しいが、
ここでの原因ではない。v1 は英語のみなので実害もない。）

**長短母音**はより深い。`ää→a` は占有率100%、つまりモデルは日本語の長母音を
一度も長母音として出していない。このマージを禁止しても「毎回ズレとして報告される」に
変わるだけで、どちらにせよ測れない。

**正規化でモデルの無能力は埋められない。** モデルが区別していない対立は、
記号をどう付け替えても測定できない。

### 結論

多言語のハードルは正規化ではなく、その**前後の2箇所**だった。
手前が G2P（漢字が読めない）、奥がモデルの言語別能力（日本語の音を区別しない）。
正規化はその間に挟まっているだけで、どちらも救えない。

1. **v1 は英語のみ。** 多言語は主張できない
2. **言語追加は「手順」ではなく「ゲート」。** コーパスでフロアを測り、
   閾値を超えたらその言語は非対応と判定する。日本語はこのゲートで落ちる
3. **モデルが区別しない対立は測定できない。** 日本語の長母音・促音がこれに当たる
4. 占有率による導出は正しいが、**それは表を作る手続きであって、
   その言語が使える保証ではない**


## 正規化層とアライメントの追確認（追記）

設計を詰める過程で、推測で書きそうになった点を実際に走らせて確かめた。

**1. 重み付けが要るのはどの列か。** 単位コストの編集距離で最小コストを数えた。

```
期待 ɡ l A s  実測 ɡ u ɹ a f s  → 最小コスト 4、最小経路が 6 本（非一意）
                                   例: l→u A→ɹ +a +f  /  +u l→ɹ A→a +f
期待 ɡ l A s  実測 ɡ u l a θ    → 最小コスト 3、最小経路は 1 本（一意）
```

**重み付けが効くのは同点になる前者だけ。** 後者は素朴な計算でも母音挿入が
正しく出るので、重み付けの論拠にならない。`ɡ u ɹ a f s` は「母音挿入が
検出された」の誇張テイクの実測列。

**2. 同一記号の連続圧縮が何を消すか。**

```
['s','s','ɪ','z'] → ['s','@','z']
```

隣接する同じ記号の挿入は、アライメントに届く前に消える。語境界で同じ記号が
隣り合う課題文（`glass sits`）の扱いを決めておく必要がある。

**3. `ɪ ʌ ə` が同じクラスに潰れる。**

```
b ɪ t → b @ t      b ʌ t → b @ t
l ɪ v → l @ v      l ʌ v → l @ v
```

`bit`/`but` は区別できない。`iː/ɪ`（`i` と `@`）や `ɹ/l`、`θ/s`、`b/v` は保たれる。
**`ɪ/ʌ` の対立は v1 では出題しない。**

**4. 声調付きの記号は等価クラス表に当たらない。**

```
['ɑ5'] → ['ɑ5']        ['ɑ'] → ['O']
```

多言語モデルは `ɑ5` `ai5` のような声調表記を出す（摂動テストで実際に出た）。
**末尾の数字は等価クラス表より前に落とす**必要がある。落とさないと同じ音が
`O` と `ɑ5` の2つの記号に割れ、置換として報告される。
