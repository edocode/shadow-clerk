# 英語の練習

英語（`en`）を練習するときに、共通の [SKILL.md](../SKILL.md) と合わせて読む。
開始・終了、聞き取り言語の切り替え、練習時間、記録の更新は共通手順に従う。

## 教材と読み方

- 発音記号は `/ /` で囲んだ米音の辞書式 IPA を使う。daemon の G2P も `en-us`。
- 単語単体や単語の羅列では出さず、一息で言える2〜6語の短い文にする。できる範囲で対象語を文頭に置かない。
- 音声認識だけのときは、対立のどちらでも成り立つ文を使う（`It's light.` / `It's right.`）。
  文脈で片方に決まる文では、発音が崩れても補われることがある。
- 発音のお手本の例: `{"text":"Turn right.","lang":"en","display":"ターン ライト（右に曲がって）"}`。
  説明中も、綴りを伏せるときは arrival ではなくアライバルなど、母語で読める形にする。
- 会話では、たとえば `I go to there yesterday.` を `I went there yesterday.` に直し、
  過去形と there の前の to について母語で説明してから言い直してもらう。
- 作文では、たとえば「昨日は雨だったので家にいました、と英語で言ってみてください」と出題する。
- 間違えたあとに正解を求めるときの言い方の例: `Please tell me the answer.`（母語の説明の中で、この英文を示す）。
- 以下の例は形式を示すもの。課題文は毎回その場で作り、固定の例文一覧として順に出題しない。

## 英語の音素フィードバック

現在の daemon の音素解析は英語のみ対応。英語でも次の API で状態を確認して使う。
英語以外に、以下の音の対立・正規化の制約・実測値を適用しない。

```
curl -s "http://localhost:8765/api/pronounce"
```

- `unavailable` なら共通手順の「音声認識だけで判定する」で進める。
- JSON が返らない古い daemon でも同じ方法を使い、以後この練習でこの API を呼ばない。
- `loading` なら以下の読み込み待ちの手順に従う。
- `idle` / `armed` なら以下の音素フィードバックを使う。`idle` は課題がまだ無い通常の状態。

課題文を daemon に預けておくと、ユーザーの発話を音素の列で突き合わせて返してくれる。
返るのは**素材だけ**で、合否も点数も入っていない。読み解くのはこちら。

**課題の出し方（音声認識だけのときと逆になる）**

- **文かキャリア文にする。裸の単語で出さない。** 単体の発話は語の端が崩れる
  （語頭の連結が母音で割れ、語末の子音が落ちる）。`Say grass again.` のように埋めると、
  その端の崩れは戻る（実測で `grass` は 9/15 → 5/5）。
  ただし**戻るのは端の崩れだけで、その人の調音そのものは戻らない**
  （同じ実測で `glass` は 7/15 → 0/5 と、むしろ落ちた）。
  単語単体はどの対立でも出さない（「教材と読み方」）
- **対立ペアを両方入れる。** `Turn right at the light.` のように1文に両方入れると、
  その発話自体が比較の基準になり、「R は出ているのに L が出ていない」という相対的な判断ができる
- **`ɪ/ʌ` の対立（bit / but など）は出さない。** 正規化で同じクラスに潰れるので測れない。
  `iː/ɪ`、`ɹ/l`、`θ/s`、`b/v` は出してよい
- 課題文に**数字を書かない**（`three times` のように綴る）
- 課題文は毎回その場で作る。例文の一覧をリポジトリに持たない

**手順**

1. 課題文は Analysis に書く（綴りを見せてよいのは AI分析 タブだけ）。最初の問題は出題の前に、
   2問目からは SKILL.md「判定のあと」の順で、お手本を読んだあとに書く
2. `POST /api/pronounce` で課題を預ける。`focus` は**語ではなく音素**で指定する

```
curl -s -X POST "http://localhost:8765/api/pronounce" -H 'Content-Type: application/json' -d '{"text":"Turn right at the light.","lang":"en","focus":[{"word":"right","phoneme":"ɹ"},{"word":"light","phoneme":"l"}]}'
```

3. 返った `expected` が、その課題文の**正規化後の期待IPA**。`focus` の `phoneme` はここに
   出てくる記号で書く。辞書どおりの記号（`iː`、`ɪ`）で送っても daemon が同じ正規化をかけるので通る。
   正規化では長音記号 `ː` が落ち、`ɪ` `ə` `ʌ` は `@`、`ɚ` `ɜ` は `R`、`ɔ` `ɑ` は `O`、`æ` は `A` になる。
   `<pronounce>` の行も `GET /api/pronounce` も、この記号で書かれる（`sit` は `s @ t`、`seat` は `s i t`）

   **拒否は HTTP 200 で `{"status":"error","message":...}` として返る。** `message` を読んで、
   次のどれかで対処する。**送り直す前に必ず何かを変える。同じ body の再送は通らない**:

   - **`expected` が付いている** — `focus` の音素がその語の期待IPAに無い。返ってきた記号を見て
     `focus` を書き直して送り直す（例: `right` の R は `r` ではなく `ɹ`）。書き直しは1回まで。
     それでも通らなければ、その音素の出題をやめる
   - **`expected` が無く、`GET /api/pronounce` の `state` が `unavailable`** — 設定が off か
     未導入。共通手順の「音声認識だけで判定する」に切り替える。**送り直さない**
   - **`expected` が無く、`state` がそれ以外** — 課題文そのものに原因がある（数字が入っている、
     未対応の言語、`focus` の語が文に無い、talk mode が動いていない等）。`message` に従って
     **課題文を作り直してから**送り直す。作り直しは1回まで。それでも通らなければ、
     従来モードに切り替えて練習を続ける
4. `display` 付きの `/api/say` でお手本を読む（綴りを見せない）
5. `[自分]` の行が届いたら、同じ通知にある `<pronounce segment_at="…" trimmed="0">…</pronounce>` の行を見る。
   daemon は解析が終わるまで（最大8秒）`[自分]` 行を止めておき、行と解析結果を続けて流す。
   **`GET /api/pronounce` を取りに行かない**。中身は attempt の要約で、一致しなかった op と `focus` の op だけが、
   `focus` を含む語から順に並ぶ（`berry: *b>v; vest: *v, ->ə; Is: z>v`）:
   - `*` が付いた op が `focus`。`b>v` は置換（`sub`）、`b>-` は欠落（`del`）、`->ə` は挿入（`ins`）、記号1つだけ（`*v`）は一致（`same`）
   - 載っていない語は全部の音が一致している。中身が空なら全部一致
   - `trimmed="1"` は下の「読み方」の `trimmed: true` と同じ。発話の文は `[自分]` 行の文で見る（`asr_text` と同じ文字起こし）
   - 長いときは末尾が `…` で切れている。`focus` の op は先頭にあるので、切れても読める
6. `[自分]` 行と同じ `segment_at` の `<pronounce>` 行が無いときだけ、`GET /api/pronounce` を1回呼んで
   `state` と `attempts`（新しい順、最大3件）を見る（下の「attempt が見つからないとき」）。
   そこでも `pending` が 0 より大きければ、その発話は**未判定**として扱い、**成否を一切言わない**
   （「解析に時間がかかっています」と母語で一度だけ伝えてよい）

```
curl -s "http://localhost:8765/api/pronounce"
```

7. `GET` で取った attempt では、`asr_text` が音声認識の結果、`words[].ops` が音素の対応

**`state` が `loading` のとき**

**`loading` は通常の動作。** 初回の POST のほか、しばらく使わずにモデルが解放されたあとの
再開でも出る。2回目以降はキャッシュから読むので数秒で済み、初回だけ 1.2GB を取得するので
数分かかることがある。

**`armed` になるまで、学習者に声を出させない。** ここで課題を出してしまうと、解析が返るのを
待たせるか、従来モードで判定して音素フィードバックの1組目を捨てることになる。

- **待つあいだに課題一覧を Analysis に書く。** どのみち声に出す前に書く作業なので、
  キャッシュ済みならこれだけで待ち時間が埋まる
- 書き終えたら `GET /api/pronounce` を取り直す。`armed` なら、そのまま課題を出す
- **まだ `loading` なら、母語で一度だけ伝えて待つ**（例:「初回なので発音の解析モデルを
  取り込んでいます。しばらくお待ちください」）。毎回は言わない。
  待つあいだは、前回までの復習など**声を出させない話**をしてつなぐ
- 読み込みが終わって `armed` になったら、そこから課題を出す
- `unavailable`（`reason` が付く）に変わったら読み込みに失敗している。そのときだけ
  共通手順の「音声認識だけで判定する」に切り替える
- アームが期限切れ（`idle`）になっていたら、同じ課題を POST し直してから続ける

**読み方**

- **まず `asr_text` が課題文全体を含んでいるか見る。** 一部しか含まないときは発話が途中で切れている。
  **その attempt では `focus` の所見を言わない**（足りない語が `del` として出るので、
  「R が出ていない」と誤って言ってしまう）。言えた扱いにもせず、続きの `[自分]` 行と attempt を見る
- **`trimmed: true` の attempt は、お手本の読み上げと重なった部分を切り落としてある。** マイクは読み上げも拾うので、
  お手本の直後に言い始めると、そこまでが1つの音声になる。切れ目に近い語（多くは文頭）は音が欠けて `del` に出ることがある。
  **文頭・文末の語の `del` は所見にしない**（欠けたのは録音で、発音ではない）。それ以外の語は普通に読む
- `words[].ops` が語ごとの音素の対応。`kind` は `same`（一致）/ `sub`（置換）/
  `del`（期待された音が無い）/ `ins`（余計な音が入っている）
- **`focus: true` の op だけにコメントする。** それ以外は、同じ語の中であってもフロア誤差。
  ネイティブの連続発話でも、正規化後の音素誤り率は平均 9.1% ある。差分がゼロになることは
  期待できないので、`focus` 以外の差分を拾わない
- **対象語だけを見る。発話全体を見ない。** キャリア文ではキャリア語のほうが派手に壊れる
  （実測で `Say` が `f e`、`again` が `a ɡ i ŋ` になる）。これは発音の問題ではない
- **この1回の発話の所見として言う。** 「あなたの L は」と傾向で断定しない。
  同じ人が同じ語を言ってもテイク間で判定が変わる
- **「何の音になったか」を言い切らない。** 相対的に言う
  （「R は出ていますが、L が R 寄りになっています」）
- **調音の助言は定型の範囲に留める。** 音の種類と位置を伝えるのが主。
  細かい口の形の指示は、確かめられていない

**attempt が見つからないとき**

お手本の回り込みや母語での発言も `[自分]` 行として transcript に残る。同じ `segment_at` の `<pronounce>` 行が
無い `[自分]` 行を見たら、`GET /api/pronounce` の `state` で分ける。

- **`unavailable`** — 音素フィードバックは使わない。共通手順の「音声認識だけで判定する」に従う。
  この節の残りは適用しない
- **`loading`** — まだ読み込み中。この行は判定せず、読み込みの完了を待つ
  （上の「`state` が `loading` のとき」）。従来モードには落とさない
- **`idle` で、課題を POST したあと `clear` していない** — **アームが期限切れ**。まず同じ課題を
  POST し直す（これが拒否されたら手順3の拒否の扱いに従う）。そのうえで、その行が
  **課題文と対応していれば**もう一度言ってもらい、**母語での発言や質問なら**普通の会話として応じる。
  `expires_at` が近いうちに（母語での質疑が長引く前に）送り直しておくと、ここに来ない
- **`idle` で、まだ何も POST していない** — 課題が無いので判定しない。普通の会話として応じる
- **`armed`** — 以下に従う

`armed` のとき:

- `pending` が 0 より大きいときは**未判定**とし（手順6。取り直さない）、
  **成否を一切言わない。** Analysis の `結果` の列は空のままにして、もう一度言ってもらう
- **`pending` が 0 で、同じ `segment_at` の attempt が無い `[自分]` 行は、試行として扱わない。**
  「言えました」とも言わない。そのうえで、行の内容で分ける:
  - **`asr_text` や行の文面が課題文と対応していない**（母語での発言・質問・相槌）→ 試行ではないので
    **普通の会話として応じる**。もう一度言ってくださいとは言わない。母語の行は
    「練習する言語の綴りを出さない」規則のためカタカナ混じりに見えることがあるので、意味で判断する
  - **課題文を言ったはずなのに attempt が無い** → お手本の回り込みなどで解析に渡らなかった。
    もう一度言ってもらう

**終わったら**

```
curl -s -X POST "http://localhost:8765/api/pronounce" -H 'Content-Type: application/json' -d '{"clear":true}'
```

`expires_at` を過ぎると自動で解ける。母語での質疑が長引いて期限が近いときは、同じ課題を送り直す。

**書く**

Analysis の語・文に結果を追記し、Advice を書き直すのは従来どおり。ただし**音素フィードバックのときは
`結果` の列に ○△× を書かない。** 観測をそのまま書く:

| 単語 | 発音記号 | 意味 | 結果 |
|---|---|---|---|
| right | /ɹaɪt/ | 右 | ɹ は出ていた |
| light | /laɪt/ | 光 | l が ɹ 寄り |

- `focus` の op が `same` なら「出ていた」。`sub` なら「<期待> が <実測> 寄り」。`del` なら「出ていない」
- **「完璧」「正解」と書かない。** ネイティブの連続発話でも、正規化後の音素誤り率は平均 9.1% ある
- Advice には**外した音と位置**を書く。音声認識の結果（何と聞こえたか）ではなく、
  どの音がどう出たかを書く
- `ins`（余計な音が入った）は「<語> の <位置> に <音> が入っている」と書く
- 試した語・文は、うまくいったものも含めて全部 Analysis に残す

## 会話中の音素解析

会話では言う文が先に決まらないので、課題文なしで預ける（`free`）。daemon は発話ごとに、その文字起こし（`asr_text`）を
期待文にして音素を突き合わせる。**おまけの情報**として扱い、会話を止めてまで待たない。

- 会話を始めるとき、`GET /api/pronounce` の `state` が `idle` / `armed` なら預ける（`unavailable` や JSON が返らないときは何もしない）

```
curl -s -X POST "http://localhost:8765/api/pronounce" -H 'Content-Type: application/json' -d '{"free":true,"lang":"en"}'
```

- 発話のたびに期限が延びるので、会話が続く間は送り直さなくてよい。発音の課題文を預けると置き換わるので、
  会話に戻るときにまた `free` を送る
- `[自分]` の行と同じ通知に、同じ `segment_at` の `<pronounce>` 行が届く。それが無ければその発話は見送る。
  `GET /api/pronounce` は取りに行かない
- **拾うのは日本語話者が崩しやすい対立だけ**: `θ` が `s` / `f` 寄り、`ð` が `z` / `d` 寄り、`ɹ` と `l` の入れ替わり、`v` が `b` 寄り、
  `f` が `h` 寄り。それ以外の差分は、自由発話ではフロア誤差（`focus` が無いので、全部の op が対象外の扱い）
- **期待文が文字起こしなので、崩れた音がそのまま別の語として認識されると差分は出ない**（thick が sick と認識されると、
  期待文も sick になる）。文脈から見て `asr_text` の語が対立の相方にすり替わっているとき（スープの話なのに sick）は、
  それ自体を所見として扱ってよい
- 指摘は**1ターンに1つまで**、文法の直しのあとに短く添える（例:「それと、シックの頭が、エス寄りでした」）。言い直しは求めない。
  同じ音が2回以上続けて崩れたら、会話の切れ目で「発音」の練習に誘ってよい
- 拾った所見は、会話の Analysis の該当の文に「発音: thick の θ が s 寄り」のように添える

## 英語の記録例

音声認識だけのときの ○△× は認識が通ったかの記録で、発音の正確さの採点ではない。
音素フィードバックを使うときは、上の「書く」に従って観測を記録する。

### Advice — いまの指摘と直し（毎回まとめ直して上書き）

```
curl -s -X POST "http://localhost:8765/api/generated" -H 'Content-Type: application/json' -d '{"kind":"advice","mode":"replace","text":"# いまの直し\n\n## 今日の重点\n- 過去のことは過去形で言う\n\n## 直近の直し\n| 言ったこと | 自然な言い方 | ポイント |\n|---|---|---|\n| I go to there yesterday. | I went there yesterday. | 過去は went。there に to は付けない |\n\n## お手本\n- 🔊[en] I went there yesterday.\n- went /wɛnt/\n\n## 発音のコツ\n- R は舌先をどこにも付けずに奥へ丸める\n"}'
```

### Analysis — 練習する語・文と記録（時刻見出しで追記）

```
curl -s -X POST "http://localhost:8765/api/generated" -H 'Content-Type: application/json' -d '{"kind":"analysis","mode":"append","text":"\n## 10:15 作文\n\n| お題 | 言えた文 | 結果 |\n|---|---|---|\n| 昨日は雨だったので家にいました | I stayed home because it rained yesterday. | ○ |\n\n次に言ってみる例文:\n\n- 🔊[en] It was raining, so I stayed home.\n- raining /ˈɹeɪnɪŋ/ ・ stayed /steɪd/\n"}'
```

発音の教材の例:

```
curl -s -X POST "http://localhost:8765/api/generated" -H 'Content-Type: application/json' -d '{"kind":"analysis","mode":"append","text":"\n## 10:20 発音 R と L\n\n| 単語 | 発音記号 | 意味 | 結果 |\n|---|---|---|---|\n| right | /ɹaɪt/ | 右 |  |\n| light | /laɪt/ | 光 |  |\n\n- 🔊[en] Turn right at the light.\n- 対象語: right /ɹaɪt/ ・ light /laɪt/\n"}'
```

> **次の2つの例は、音声認識だけで判定しているときのもの。** `結果` の ○× も「舌先を付けない。唇を少しすぼめる」のような
> 細かい口の形の指示も、音素フィードバックが使えるときには書かない（上の音素フィードバックの「書く」に従う）。

```
curl -s -X POST "http://localhost:8765/api/generated" -H 'Content-Type: application/json' -d '{"kind":"analysis","mode":"append","text":"\n### 10:22 結果と直し\n\n| 単語 | 発音記号 | 結果 | 聞こえ方 | 直し |\n|---|---|---|---|---|\n| right | /ɹaɪt/ | 1回目 ×、2回目 ○ | light | 舌先を付けない。唇を少しすぼめる |\n| light | /laɪt/ | ○ |  |  |\n"}'
```
