# 誰も答えられない話題を調べる

会議では「あれ、どうなったんでしたっけ」「たしか〜だったはず」で止まることがある。
その場で答えが出れば議論が進むので、**調べて返す**のがいちばん効く。

## いつ出すか

出す:

- 事実を問う質問が出て、**参加者の誰も答えられなかった**
- 「前回どうなったか」「誰が担当だったか」「いつ決めたか」で全員の記憶が食い違っている
- 出てきた用語・仕様・製品を、参加者が知らないまま議論が進んでいる
- 「あとで調べます」で流れた — その「あとで」を今やる

出さない:

- 会議の場で答えが要らないもの（持ち帰り前提の調査）
- 意見や判断を問うもの。調べても答えは出ない
- **`forbid-ai-analyze.txt` に挙がっている話題**。分析しないものは調べもしない

**1 周回に 1 件まで。** 監視は 25 秒ごとに起きるので、毎回投げると調査ばかりになる。

## 調べるのはサブエージェント

**自分で検索や `Read` をしないこと。** ファイルも Web ページも 1 件で数千トークンあり、
監視に使う context が尽きる。Task ツールに投げて、**答えと根拠だけを返させる**。

探す先は 4 つ。**上から順に当たらせる**。

1. **起動ディレクトリ以下** — 設定の `workdir`。コード・設計文書・過去の議事録
2. **過去の会議** — `/api/meeting-history` が返す transcript / summary / advice
3. **サブエージェント自身の知識** — 規格・仕様・一般的な実装は、たいてい**すでに知っている**。
   検索するまでもない。ただし**バージョンや最近の変更は当てにならない**ので、
   確度を必ず添えさせる
4. **設定で許可された外部の当て先** — 下記

**3 で足りるなら 4 に行かない。** 4 が要るのは、3 が知らないとき（最近の変更、特定の
製品のドキュメント、バージョン依存の挙動）と、社内の当て先に実データを聞くとき。

依頼文:

> 会議中の質問です。**2 分以内**に、答えと根拠だけを返してください。本文や
> ページの引用は貼らず、結論を 3 行以内で。
>
> **質問**: <発言から起こした問い>
> **文脈**: <直前 5〜10 行の発言>
>
> 探す順:
> 1. `<workdir>` 以下（コード・設計文書・議事録）
> 2. 過去の会議の議事録: `<meeting-history のパス>`
> 3. あなたの知識（規格・仕様・一般的な実装。バージョン依存の話は確度を落として）
> 4. `<research の当て先と allow_private>` — 許可されたものだけ
>
> 返す形:
> - **答え**: 1〜2 行
> - **根拠**: ファイルパスか URL。**どこにも無ければ「見つからず」と書く**
> - **確度**: 確定 / 推定 / 不明
>
> 見つからないものを埋めないでください。「見つからず」が正しい答えです。

## 4 の当て先は設定で決まる

`/api/mtg-config/resolve` の `research` に、**許可された当て先だけ**が並んでいる。

```yaml
defaults:
  research:
    - name: bigquery
      allow_private: true       # 社内。そのまま聞いてよい
      note: 会員数などの実データ
    - name: web                 # 既定は allow_private: false
```

**`research` が空なら 4 は使わない。** 1〜3 で答えて、足りなければ「見つからず」と返す。
このマシンの外へ問い合わせるものは、明示的に許可されたものだけにしてある。

**`allow_private` は当て先の属性で、話題の属性ではない。** 社内の情報を渡してよい
当て先か、という意味。**既定は `false`**（書き忘れたら社外として扱う）。

| `allow_private` | 意味 | 問いの作り方 |
|---|---|---|
| `true` | 社内の当て先（自社の DWH・課題管理・社内 wiki など） | **そのまま聞く。** 社名も製品名も実データも、そこにあるものを聞くのだから隠す意味がない |
| `false`（既定） | 社外へ出る（Web 検索、外部サービス） | 下の 2 段で作り直す |

「会員数は何人だったか」を社内の DWH に聞くのは、**社内の情報を社内で調べている**だけ。
社内情報だからという理由で落とさない。落とすべきなのは、それを**社外へ**出すときだけ。

## `allow_private: false` の当て先へ渡す問い

### 1. その下にある一般的な問いを書く

**発言から語を削って作らない。** 「この人たちが本当に知りたいことは何か」を、
一般的な用語だけで書き起こす。固有名詞は入れない——**例外は、社外の誰もが同じものを
指すと分かるもの**（公開されている製品名、規格名、OSS 名など）だけ。

**社内システムの挙動を聞いているように見えても、その下にある一般的な問いはたいてい
存在する。** 規格がどう定めているか、一般的な実装はどうか。それを聞く。

| 会議で出た問い | 渡す問い |
|---|---|
| 「〈社内の認証基盤〉の sub は〈社内の管理画面〉のクライアントと跨いで同一か」 | 「OIDC で sub は client を跨いで同一か。pairwise と public の違い」 |
| 「〈社内基盤〉のリトライは何回で諦めるのか」 | 「一般的な webhook 配信のリトライ回数と間隔の設計」 |
| 「〈取引先〉との契約は何年更新だったか」 | 渡さない（下記） |

### 2. 用語集で照合する

用語集(glossary)と `attendees` には社名・個人名・サービス名が登録されている。
**1 で書いた問いにこれらの語が含まれていたら、1 が失敗している。** 削って済ませず、
書き直しからやり直す。

**照合は網であって、定義ではない。** 用語集は完全ではないので、**載っていない語なら
出してよい、ではない**。1 の「固有名詞は入れない」が本則。

### 渡さないのは

**聞いているものが、その組織でしか答えの無い事実そのもの**のとき。契約の条件、
社内で決めた設定値、誰が何をしたか、自社データの中身。これらは一般化すると
問いが消えるので、`allow_private: true` の当て先か 1〜3 で答える。

**「自社システムの話だから」は理由にならない。** 上の表の 1 行目・2 行目がそれで、
主語は社内でも、答えは規格と一般的な実装の側にある。

## 返ってきたら

`advice` の「いま確認すべきこと」に、**その場で言える文言**として置く。

```markdown
## いま確認すべきこと
> 「その件、前回(8/27)の議事録では『次スプリントで対応』で止まっています。
>   担当は決まっていないので、ここで決めませんか」
```

**確度をそのまま渡す。** 「確定」なら根拠のパスごと、「推定」なら推定と明記して
検証方法を添える。**会議で発言される前提なので、誤った断定は害になる。**

**「見つからず」も返す価値がある。** 全員の記憶が曖昧なまま議論が進むより、
「記録が無い」と分かったほうが決めやすい。

**間に合わなかったら黙って捨てない。** 話題が移っていても、
「さきほどの件ですが」と付けて出す。決まったことが誤った前提に基づいていたなら、
それは最優先で伝える。
