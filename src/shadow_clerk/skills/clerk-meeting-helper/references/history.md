# 定例の過去回を読む

`/api/session` の `meeting` が空でなく（カレンダー連携で名前が付いている）、
設定の `history` が 1 以上のときだけ行う。1 回きりの会議では空振りする。

```bash
curl -s "$SHADOW_CLERK/api/meeting-history?meeting=<会議名>&count=<history>"
```

`meetings` に新しい順で `datetime / meeting / transcript / summary / advice / analysis`
が入る（存在しないファイルの欄は空文字）。進行中の回は含まれない。

**`summary` / `advice` / `analysis` がすべて空の回は、生の文字起こししか残っていない。**
その回しか無いなら、**読ませるのは直近 1 回だけにする**。3 回ぶんの生 transcript は
数万トークンかかるわりに、返ってくるのは「宿題は無かった」程度のことが多い。
議事録が 1 つでもある会議なら、`history` の数だけ読ませてよい。

照合は会議名の正規化一致（大文字小文字と区切りを無視）で、サーバ側が行う。
設定の `matched` パターンは会議の同一性ではない——`Standup|Sprint[ _-]?MTG|…` は
`Sprint_MTG` と `Platformチーム_Standup` という**別々の定例に同時に当たる**。

## 読むのはサブエージェント

議事録は 1 回あたり数百行あり、3 回分を本体で読むと監視に使う context が残らない。
**Task ツールでサブエージェントに読ませ、下の 4 点だけを返させる。**

渡すのは `meetings` のパスと、いま何を見たいか。依頼文:

> 次の過去回のファイルを読んで、今日の会議で使える形にまとめてください。
> 本文は返さず、下の 4 点だけを箇条書きで返してください。
>
> ```
> <meetings のパス一覧>
> ```
>
> 1. **前回時点で未解決だったもの**（`advice` が最も正確。無ければ議事録の未解決節）
> 2. **宿題のうち、期限が今日または過ぎているもの**（担当と期限つき）
> 3. **前回の決定事項**のうち、今日の議題に関係しそうなもの
> 4. **毎回出て決まっていない論点**（複数回に現れるもの）
>
> 読む優先順位は `advice` → `summary` → `analysis`。長い議事録は
> 決定事項と宿題の節だけで足りることが多い。
>
> **見出しが 1 つも無いファイルは読まずに飛ばしてください。**
> 生成が途中で打ち切られた壊れたファイルで、数百行を読んでも何も得られません
> （実データ 408 件のうち 38 件がこれ。`Thinking Process:` などで埋まっている）。

正常な議事録は `# 議事録` / `## 概要` / `## 主要トピックと決定事項` /
`## アクションアイテム` という構成になっている。

## 返ってきたものをどう使う

読むだけでは効かない。会議中に次を見る。

- **前回の宿題で期限が今日、または過ぎているもの** — 触れられないまま終わりそうなら指摘する
- **前回の未解決が今回も議題に上がっていない** — 繰り返し先送りされている論点
- **今回の議論が前回の決定と矛盾していないか** — 決め直しなら、決め直しだと明示させる
- **毎回出て決まらない論点** — 3回続けて出ているなら、決め方そのものに問題がある

第一報に **「前回（M/D）から: 未解決N件、期限が来ている宿題N件」** を入れる。
これが会議の冒頭でいちばん効く。
