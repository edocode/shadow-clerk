# ダッシュボードからの音声デバイス選択とレベル表示

作成日: 2026-08-10
改訂: 2026-08-10（high-effort レビューの指摘を反映して全面改訂）

## 背景

2026-08-10 の会議中、shadow-clerk が「自分」の発話を 1 行も記録しない事象が発生した。原因は PipeWire のデフォルト入力が内蔵の Ryzen Digital Microphone（常時 RMS 約 2760・クレストファクタ 1.3 の定常ハムしか出さない実質死んだデバイス）になっていたことだった。ユーザーは Shokz Loop110 のヘッドセットに向かって話しており、会議アプリはそちらを明示指定していた。

shadow-clerk のマイクは `device=None`（PortAudio の `default`）で OS のデフォルト入力を辿るため、デフォルトが壊れたデバイスに落ちると無言で壊れる。ストリーム自体は正常にフレームを供給し続けるので、フレーム途絶ウォッチドッグには引っかからず、ダッシュボードも `use_mic: true` を表示し続ける。

この設計は 2 つの問題に対応する。

1. **選べない**: shadow-clerk が使うデバイスを OS の設定を触らずに指定できない
2. **気付けない**: 意図しないデバイスを掴んでいても、ダッシュボード上で判別できない

### 初版からの変更点

初版の設計はレビューで 10 件の指摘を受け、うち中核の 1 件が構造的欠陥だった。初版は張り替えトリガを「設定値 ≠ 現在開いているデバイス名」の 1 つだけで表現していたが、この条件は**自動フォールバック中に永久に真**になる。指定デバイスが消えている間ずっと再接続を繰り返し、「消えても録音を止めない」というゴールと正面から矛盾していた。本改訂ではトリガを 2 つに分離してこれを解消する（後述）。

また PR #17 で再接続の待機が見直され、生きたストリームがある場合は待機なしで張り替わるようになった。本設計はその挙動を前提とする。

## ゴールと非ゴール

**ゴール**

- ダッシュボードからマイク／スピーカー（モニター）を指定できる
- 入力レベルが常時見え、意図しないデバイスや無音状態にその場で気付ける
- 指定したデバイスが消えている間も録音を止めない。戻ってきたら自動で復帰する
- 上記を sounddevice 経路と pw-record/parec 経路の**両方**で成立させる

**非ゴール**

- OS のデフォルトデバイスを書き換える機能（`wpctl set-default` 相当）は作らない。OS の状態を書き換える上に PipeWire / PulseAudio / Windows で実装が分かれるため
- 異常時の通知やログ警告（デスクトップ通知等）は作らない。ダッシュボード上の表示にとどめ、気付くかどうかは人間に委ねる
- Windows（WasapiBackend）でのデバイス選択。本設計は Linux（PipeWire/PulseAudio）を対象とする。Windows では設定キーを無視し、従来通り自動検出する

## 設定

`DEFAULT_CONFIG`（`_daemon_constants.py`）に 2 キーを追加する。値は**デバイス名**であり、番号ではない。デバイス番号は起動ごとに変わり、稼働中にも移動する（`CLAUDE.md` の Known Pitfalls 参照）。

```yaml
mic_device: null       # null = 自動（OS のデフォルト入力に追従）
monitor_device: null   # null = 自動（デフォルト Sink の .monitor）
```

`_save_config`（`_daemon_dashboard_ops_config.py`）は `DEFAULT_CONFIG` のキーを走査して保存するため、保存側の変更は不要。

CLI の `--mic` / `--monitor`（番号指定）は互換性のため残し、指定時は config より優先する。CLI で番号を指定した場合、config の値は無視され、以降のデバイス選択 UI は「CLI で固定中」と表示して操作不能にする。2 つの指定手段が同時に効いて張り替えが競合するのを防ぐため。

## デバイス解決とフォールバック

`resolve_mic_device` / `resolve_monitor_device` を「設定名 → 実デバイス」の解決に拡張する。

1. 設定に名前があり、その名前のデバイスが一覧に存在する → それを開く
2. 設定に名前があるが一覧にない、**または開こうとして失敗した** → 自動にフォールバックして開く。設定値は書き換えない
3. 設定が `null` → 従来通り自動

規則 2 に「開けなかった場合」を含めるのが初版からの修正点である。初版は「一覧にない場合」だけをフォールバック条件にしながら、エラー処理の節では「開けない場合もフォールバックする」と書いており矛盾していた。列挙はできても他アプリが排他的に掴んでいて開けないケースは実在するため、`_open_capture` が失敗したら自動で開き直す。

### 張り替えトリガ

`_CaptureStream` は「開いた時点で要求されていた設定値」を `requested` として保持する（`null` = 自動）。監視ループは次の 2 つを独立に見る。

| トリガ | 判定周期 | 条件 |
|---|---|---|
| 設定変更 | 2 秒（`STREAM_CHECK_INTERVAL`） | `load_config()[<label>_device] != stream.requested` |
| 指定デバイスの復帰 | 10 秒（`STREAM_RESOLVE_INTERVAL`） | フォールバック中（`requested` が非 null かつ `device.name != requested`）で、かつ `requested` のデバイスが**実在する** |

この分離が初版の欠陥を解消する。フォールバック中は 1 つ目の条件が偽（設定値は変わっていない）で、2 つ目もデバイスが存在しない限り偽なので、**静止する**。設定が変われば 2 秒以内に反映され、指定デバイスが戻れば 10 秒以内に復帰する。

設定値の読み取りに `load_config()` を使う（mtime キャッシュがあるため 2 秒ごとでも実質無コスト）。`_api_configured` の教訓どおり `__init__` でキャッシュしない。

### デフォルト Sink 追従との関係

モニターの `follow_sink`（デフォルト出力先の変更で張り替える既存の仕組み）は、現状 `self.args.monitor is None` だけを条件にしている。config で `monitor_device` を固定した場合も `follow_sink` が真のままになり、出力先を切り替えるたびに**同じデバイスを開き直すだけの無駄な張り替え**が起きる。

条件を「CLI でも config でもモニターが固定されていない場合のみ真」に改める。ユーザーが明示的にモニターを固定したなら、デフォルト Sink が変わっても追従してはならない。

### 「デバイスが実在するか」の判定

PortAudio の一覧はキャッシュであり、再列挙には全ストリームの破棄が必要になる。したがって「ヘッドセットを挿し直したか」をキャッシュで判定することはできない。

そこで復帰判定には **OS 側の一覧**（`wpctl status --name` / `pactl list short`）を使う。`_daemon_audio.py` に `device_exists(name) -> bool | None` を追加する。`None` は OS 側の一覧を取得できなかったことを表し、その場合は復帰判定を行わず、既存の degraded 再試行（指数バックオフ）に任せる。

照合には 2 つの実測上の注意がある。初版はどちらも見落としており、モニターの復帰判定が常に失敗していた。

- **`.monitor` は OS の一覧に出ない**。マイクの名前は PipeWire のノード名と一致するが（`alsa_input.usb-Shokz_..._mono-fallback`）、モニターの PortAudio 名は「sink 名 + `.monitor`」であり、`wpctl status --name` は sink（`alsa_output.usb-Shokz_...analog-stereo`）しか列挙しない。したがって名前が `.monitor` で終わる場合は接尾辞を落として sink の存在を見る。モニターソースは対応する sink があれば必ず存在する
- **部分一致は誤判定する**。PortAudio は `pipewire` や `default` という名前のデバイスを持ち、`wpctl` の出力にはヘッダ行の `pipewire-0` が含まれる。行をトークンに分割してノード名と完全一致で比較する

**選択肢は PipeWire ノード名のデバイスに限る**。PortAudio は生 ALSA デバイス（`HD-Audio Generic: ALC257 Analog (hw:1,0)`）も列挙するが、これらは wpctl のノードではないため `device_exists` で検証できず、復帰判定が働かない。加えて生 ALSA デバイスを掴むとサウンドカードを排他確保し、他アプリの音を壊す。したがって UI に出すのは `alsa_input.` / `alsa_output.` で始まる名前だけとし、そのようなデバイスが 1 つも無い環境（PipeWire/PulseAudio 不在）でのみ全件表示にフォールバックする。

これは `get_default_sink_name()` と同じく 10 秒ごとに 1 回のサブプロセス呼び出しで済む。

## 再接続の粒度

現状はどの理由でもマイクとモニターの両方を閉じ、`refresh_device_list()` を呼んでから開き直す。`Pa_Terminate` が全ストリームを破棄するためだが、出力先を切り替えただけでマイクの音声まで失われる。

再列挙が必要なのは「目的のデバイスがキャッシュ上の一覧に無い」場合だけである。そこで `_watch_streams` の戻り値を「理由の文字列」から「張り替え対象のラベル集合 + 再列挙が必要か」に変え、監視ループを次のように分岐させる。

- **再列挙が必要**（フレーム途絶、または目的のデバイスがキャッシュにない）→ 従来どおり全ストリームを閉じて `refresh_device_list()` してから開き直す
- **不要**（設定変更で、選ばれたデバイスがキャッシュ上に存在する）→ **該当するストリームだけ**を閉じて開き直す

ダッシュボードから選び直す操作は後者に該当するため、もう一方の系統の音声は途切れない。フレーム途絶からの復帰は前者のままである（ノードが作り直されている可能性が高く、再列挙が要る）。

## バックエンド（pw-record / parec）経路

sounddevice でモニターを開けない場合、`_monitor_backend_thread` が pw-record/parec でキャプチャする。初版の設計はこの経路に一切触れておらず、`monitor_device` が無言で効かないままレベルも永久に `null` になっていた。

- **デバイス指定**: `pw-record --target` は「serial or name」を受け付ける（`--help` および実機で確認済み）。`parec --device=` も名前指定である。したがって `monitor_device` が設定されていれば `detect_monitor_source()` の結果の代わりにその名前を渡す。設定が `null` のときのみ従来の自動検出（wpctl のデフォルト Sink ノード ID）を使う
- **レベルと生存監視**: 後述の `CaptureLevel` を `_capture_pcm_stream` からも更新する。これによりこの経路でもレベルが出る上、**フレーム途絶の検知が可能になる**

  現状 pw-record が生きたままフレームを出さなくなると `proc.stdout.read` で永久にブロックし、モニターが無言で死んだままになる。検知は `_capture_pcm_stream` 自身が行う。監視スレッドは子プロセスを保持していないため外から止められないからである。読み出しを `select.select([proc.stdout], [], [], STREAM_STALL_SEC)` で待ち、タイムアウトしたらループを抜ける。既存の `finally` が `proc.terminate()` / `proc.wait()` を実行し、`_monitor_backend_thread` のループが再検出して開き直す。

  `select` が読み出し可能を報告してから `read(FRAME_SIZE * 2)` を呼ぶと、1 フレーム未満しか届いていない場合にそこでブロックしうる。フレーム境界の管理は呼び出し側で行い、`os.read` で届いた分だけ読んでバッファに貯める形に変える

## レベル計測

ラベル（`mic` / `monitor`）ごとに `CaptureLevel` アキュムレータを持ち、**recorder の属性として公開する**（`self.levels: dict[str, CaptureLevel]`）。初版は `_CaptureStream` にレベルを持たせる設計だったが、`_CaptureStream` は監視スレッドのローカル変数であり `FileWatcher` から到達できないため、そのままでは実装できなかった。

- `_CaptureStream._callback`（sounddevice 経路）と `_capture_pcm_stream`（バックエンド経路）の両方が、同じ `CaptureLevel` を更新する
- 480 サンプルの numpy 演算なので、毎秒 33 回の呼び出しでも負荷は無視できる
- `CaptureLevel.snapshot()` が直近 1 秒の値を返して窓をリセットする

戻り値は `domain/audio_level.py` に置く不変の値オブジェクト `AudioLevel` とする。

- `rms`: 平均音量
- `peak`: ピーク
- `crest`: `peak / rms`（クレストファクタ）。`rms` が微小（1 未満）のときは 0 を返す。無音時の 0 除算を避けるため

クレストファクタを出すのは、今回の切り分けで決め手になった指標だからである。音声なら 3〜10 以上、定常ノイズなら 1〜2 になり、「デバイスは開けているがノイズしか来ていない」状態を数値ひとつで判別できる。実測値は内蔵マイク 1.3 / Shokz 49.4 だった。

## 配信経路

`/api/status` のポーリングは 10 秒間隔（`_daemon_dashboard_js_panels.py:182`）でメーターには遅すぎる。一方 `FileWatcher.run()`（`_daemon_log_buffer.py:126`）は既に 1 秒周期で回り、SSE で `transcript` / `log` / `ptt` などを配信している。

`FileWatcher._poll()` に `level` イベントを追加する。`self._recorder.levels` 経由で到達できるため、追加のスレッドもポーリング経路も不要。

```json
{"mic": {"rms": 34.3, "peak": 1799, "crest": 52.4,
         "device": "alsa_input.usb-Shokz_...", "requested": "alsa_input.usb-Shokz_...",
         "fallback": false},
 "monitor": {"rms": 0.0, "peak": 0, "crest": 0.0,
             "device": "alsa_output...monitor", "requested": null, "fallback": false}}
```

`fallback` は「設定でデバイスを指定しているが、それが見つからず自動で代替中」を表す。系統がまったく開けていない場合は `null` を返す。

1Hz + ピークホールドは VU メーターとしては粗いが、「マイクが生きているか」の判断には十分であり、既存ループに相乗りできる利点が上回る。

## UI

**ヘッダー（常時表示）**

既存のミュートボタン（🎤 / 🔊）の**隣に独立した要素として**レベルバーを 2 本置く。初版はミュートボタン自体に警告色と tooltip を載せる設計だったが、`updateMuteBtn`（`_daemon_dashboard_js_core.py:326-332`）が 10 秒ごとに `title` と class を無条件に書き直すため、1Hz の `level` ハンドラと奪い合いになる。所有権を分けるため、レベルと警告は専用の `<span>` が持つ。

- バーの長さは RMS を対数スケールで表示する
- **定常ノイズ警告**: 直近 10 回（= 10 秒）の `level` イベントがすべて「`rms` >= 100 かつ `crest` < 2」を満たしたらバーを警告色にする。`rms` の下限を課すのは、無音時に `crest` が 0 になって誤検知するのを防ぐため。判定はブラウザ側で行い、サーバは生の値だけを送る
- `fallback` が真のときはバーの脇に警告アイコンを出し、tooltip に指定デバイス名と代替中である旨を表示する

**設定パネル**

セレクトボックスを 2 つ追加する。先頭の選択肢は「自動（OS のデフォルト）」（= `null`）。CLI で番号指定されている場合は無効化し、その旨を表示する。

**デバイス一覧 API**

`GET /api/audio-devices` を新設し、`_daemon_dashboard_base.py` のルーティングに追加する。

```json
{"mic": [{"name": "...", "label": "..."}],
 "monitor": [{"name": "...", "label": "..."}],
 "updated_at": 1786500000.0}
```

一覧は監視スレッドが保持するスナップショットを返す。**スナップショットはストリームを開くたびに更新する。初回の起動時も含む。** 初版は「再接続のたび」としていたため、正常に動いている機械では再接続が起きず、セレクトボックスが永久に空のままだった。`sd.query_devices()` はキャッシュの読み出しなので、開くたびに取っても実質無コストである。

これで通常は「更新」ボタンなしで一覧が埋まる。抜き差し直後などスナップショットが古い場合に備えて明示的な「一覧を更新」ボタンも置くが、これは再列挙（全ストリームの張り替え）を要求するため、tooltip に音が一瞬途切れる旨を明記する。

`label` は人間が読める表示名とする。PipeWire のノード名は一意だが読みにくいため、`sd.query_devices()` の情報から整形する。`name` が実際のキーであり、`label` は表示専用。

## i18n

新規の文字列（セレクトのラベル、「自動（OS のデフォルト）」、フォールバック時の tooltip、「一覧を更新」、CLI 固定中の表示）は `_i18n_ja.py` / `_i18n_en.py` に追加し、`t()` 経由で参照する。ダッシュボード側は既存の `{{i18n:key}}` プレースホルダと `/*I18N_JSON*/` の仕組みに従う。

## エラー処理

- 指定デバイスが一覧にない → 自動にフォールバックし、`fallback: true` を配信
- 指定デバイスは一覧にあるが開けない（`PortAudioError`）→ `_open_capture` のリトライ（1 回）を経て、自動にフォールバック
- 自動でも開けない → 既存の degraded 経路で指数バックオフ再試行（30 秒 → 最大 300 秒）
- `/api/audio-devices` がスナップショット未生成の状態で呼ばれた（起動直後のごく短い間）→ 空配列と `updated_at: null` を返し、UI は「検出中」と表示する

## 検証

テストフレームワークがないプロジェクトのため、検証はスクリプトで行う（既存の watchdog 検証スクリプトと同じ方式）。

1. **フォールバック中に静止すること**（初版の欠陥の回帰テスト）: 存在しない名前を設定 → 自動にフォールバックし、その後 30 秒間ストリームが張り替わらないこと
2. **復帰**: フォールバック中に指定デバイスが OS 一覧に現れたら 10 秒以内に張り替わること
3. **設定変更の反映**: 稼働中に config を書き換え → 2 秒以内に該当ストリームだけが張り替わり、もう一方のフレームが途切れないこと
4. **開けない場合のフォールバック**: 一覧にあるが `open()` が失敗するデバイスを指定 → 自動にフォールバックすること
5. **レベル計測**: ダミー波形（無音・正弦波・定常ノイズ・バースト）を流し、クレストファクタが期待値（無音は 0、正弦波は約 1.41、ノイズは 1〜2、バーストは 3 以上）になること
6. **バックエンド経路**: `monitor_device` が `pw-record --target` に渡ること、フレームが止まったら子プロセスが終了・再検出されること
7. **実機確認**: ダッシュボードのセレクトを切り替えてマイクが張り替わること、レベルバーが動くこと

## 実装順序

初版より範囲が広がっているため、2 段階に分けて実装・検証する。各段階は単独で動作し、単独で価値がある。

**第 1 段階（デバイス選択）**: 設定キー、解決の拡張、トリガ 2 系統、`device_exists()`、張り替えの粒度、`follow_sink` の条件、バックエンド経路への名前指定、`/api/audio-devices`、設定パネルのセレクト、ドキュメント更新。これだけで「OS を触らずに指定できる」というゴールが満たされる。

**第 2 段階（レベル表示）**: `AudioLevel` / `CaptureLevel`、両経路からの更新、バックエンド経路の生存監視、`level` SSE イベント、ヘッダーのレベルバーと警告表示。これで「気付ける」というゴールが満たされる。

第 2 段階に含めたバックエンド経路の生存監視は、`CaptureLevel` の更新時刻をそのまま流用するため、レベル計測と同じ段階に置くのが自然である。
