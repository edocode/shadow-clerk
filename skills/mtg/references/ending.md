# 監視の停止と議事録

**このファイルを読むのは、終了らしいと判断したあと。** 判定そのものは SKILL.md の
「会議の終了判定と停止」にある。

## 止める前に客観的な事実を取る

```bash
curl -s "$SHADOW_CLERK/api/session"
tail -3 <transcript>
```

**`in_meeting` が `true` なら止めない。** shadow-clerk はカレンダー連携で会議の終了を
知るので、これが `true` である限り会議は続いている。実行を省略しないこと。
`tail` では末尾に `--- 会議終了 ---` が書かれているかを見る。これは shadow-clerk が
書く客観的な事実で、あれば確定。

監視を誤って止めると、その間の発言は Monitor から流れてこないので取りこぼす
(あとから `sed` で拾えるが、その間の指摘は手遅れになる)。

## ユーザーのゲートを通す

**終了を検知しても、議事録を作り始めない。** 停止と議事録作成は、どちらもユーザーの
明示的な指示があってから行う。こう返して待つ:

> 双方の挨拶で締まりました。監視を止めて議事録を作りますか。(y/n)

答えをもらってから `TaskStop` → 議事録作成に入る。

**例外: shadow-clerk からの依頼。** 会議終了時に

> 会議が終了しました。<transcript> の議事録を作成し、<summary のパス> に書いてください。

という依頼が届くことがある（`auto_summary_via_console` が有効な場合）。これは
**ユーザーの指示にあたる**ので、そのまま作ってよい。この門はアシスタントが勝手に終了を
判断して作り始めるのを防ぐためのもので、shadow-clerk は `end_meeting` を確かに知っている。
書き込み先は依頼に含まれるパスに従うこと。

## 議事録の構成

1. 会議情報(日時・出席・目的)
2. 結論(3〜4点。読み手が最初に知るべきこと)
3. 決定事項(条件つきのものは条件ごと)
4. 判明した事実
5. リスクと未解決論点(重要度つき)
6. 宿題(担当別。期限が決まっていないものはそう明記する)
7. 未決のまま終了した項目

素材は transcript だけでなく、会議中に書いた `analysis`(時系列の確定事実)と
`advice`(終了時点の未解決)がある。5 と 7 は `advice` の残りがそのまま使える。

社外との会議なら、**発言者は社名・役割で書く**(話者判別ができていないため)。
文字起こしをもとにした再構成であることも添えると、後から読む人が精度を判断できる。

## 公開の可否

設定の `publish` が `false` の会議では、**議事録を Artifact として公開しない。**
会話で返すこと、ローカルの `.md` に書くことは制限しない。制限するのは外部サービスへ
出す部分だけで、理由は「特定個人に関する内容が外部に置かれるのを避ける」ため。
求められたら Markdown ファイルとして手元に出す。

`publish` が真なら、共有される成果物なので Artifact として公開してリンクを渡すのが
扱いやすい。Markdown で欲しいと言われたらそちらで出す。
